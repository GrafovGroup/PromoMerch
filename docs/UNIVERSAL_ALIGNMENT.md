## Purpose and provenance

The PromoMerch prompt adapts the complete universal standard to a quote-led branded merchandise business and the planned MerchMatters rebrand. It retains the standard's named phases, bilingual customer journey, factual safeguards, design preferences, meaningful verification and recoverable source requirements. ## Explicit project decisions and overrides

- **Selected identity:** 1A — Refined Slash, selected by the owner “for now.” It is the implementation direction; do not restart logo exploration or seek the same selection again.
- **Visible name:** PromoMerch, with no `.ca`, no separate emblem and no additional decorative symbol. This overrides a generic domain-as-logo default. The website domain remains `promomerch.ca`.
- **Descriptor:** BRANDED MERCHANDISE on one line aligned directly underneath the wordmark. Preserve the approved English artwork. The French descriptor in the project prompt is a documented translation default, not a previously approved new slogan.
- **Approved concept versus production artwork:** the supplied PNG is the selected reference board, not a finished editable or transparent logo package. Production work must preserve the reference and record any reconstruction/fidelity work accurately.
- **Current authorization:** prepare the master-prompt package and upload it to the specified GitHub repository. This does not request building, deploying, changing DNS/email, activating redirects or announcing the rebrand.
- **Future execution:** APPROVED_BRAND_BUILD when an implementation is requested; RESUME when useful implementation already exists. Later instructions determine release scope. Do not introduce phase-by-phase approval rituals.
- **Business-specific application:** quote-led merchandise catalogue, product shortlist, project brief, reorder enquiry and MerchMatters migration planning. Checkout, instant pricing, live stock, accounts and company-store portals are not implicit launch requirements.
- **Legacy continuity:** keep the observed MerchMatters legal seller and contact channels distinct from proposed new-brand details until the transition is established. Project ownership is not proof that the contracting entity has changed.

## Later universal overlay: complete favicon coverage

The owner subsequently required a functioning favicon across every page and browser context where supported. The WindowServices reference explicitly carries this later requirement forward. Original universal v2.0 includes favicon and icon checks but does not contain the expanded dedicated coverage section used here.

PromoMerch Section 16 and its acceptance checks apply the later requirement through shared template declarations, real icon formats, deep EN/FR route coverage, small-size legibility and truthful reporting of the browsers/devices actually tested. A functional small icon derived from the approved M/slash does not introduce a new standalone brand emblem. Search-engine favicon display is not guaranteed.

## Review scope

The complete universal source and the complete PromoMerch prompt were read and compared during preparation. This alignment review concerns the written requirements. It is not evidence that the website, production logo exports, form delivery, hosting, browser coverage, deployment or search submission have been implemented or tested. Actual execution evidence belongs in the project status and launch checklist.
