## 6. PHASE 1B — DISTINCTIVE DESIGN AND FOUNDATION

Apply these shared preferences while giving each brand its own composition:

- Use wide fluid layouts with sensible gutters across desktop sizes. Let media, grids, and backgrounds use space; constrain long prose to readable line lengths. No fixed narrow container on a large screen and no horizontal overflow on mobile.
- Use uppercase primary navigation and buttons, concise labels, rounded buttons, and restrained iconography. A radius around 12 px is a starting point, not a universal requirement.
- Omit gratuitous arrow decorations from buttons, links, cards, and headings. Preserve functional direction indicators such as menu disclosure controls when needed.
- Use one consistent header, primary menu, and footer across equivalent routes. Highlight the active item without changing the menu's contents. Translate labels without changing the underlying navigation structure.
- Put the visible FR / EN language control in the top utility bar, with an accessible position on mobile. Give the logo enough size and contrast to remain legible.
- Default commercial navigation to concise offering, audience, location, and resource categories that actually exist. Put ABOUT in the footer by default and omit redundant “OUR” in menu/footer labels. Give ownership/editorial information more prominence where a regulated or information resource needs it.
- Build a focused hero with a specific proposition, short supporting copy, relevant imagery, and one primary action. At typical laptop sizes, let the next section become apparent without making the hero cramped. Test height and crop on real viewports rather than applying a fixed full-screen hero everywhere.
- Make the mobile menu align correctly, scroll safely, close predictably, restore focus, and work by keyboard. Sticky call/quote actions must not cover content, form controls, or accessibility controls.
- Use purposeful spacing, clear hierarchy, varied section composition, and a small amount of useful motion. Avoid repetitive card grids, generic gradient blobs, fake counters, template slogans, autoplay distractions, and motion that hides content when scripts fail.
- Support reduced-motion preferences. Keep decorative animation subordinate to comprehension and speed.
- Remove unsolicited builder credits, AI badges, and generic AI disclaimers. Retain required attribution and any material context needed to avoid misleading people.

Preserve an existing site's approved visual choices unless a redesign is requested. Do not apply another brand's exact colour scheme, hero layout, slogan, logo geometry, or service priorities as a universal default.

## 8. PHASE 1C — CONVERSION AND ENQUIRY DELIVERY

Build the complete main-action journey in both languages. Telephone links use a valid international number; email links use the correct brand inbox. Avoid excessive popups and unnecessary required fields.

Keep the initial form concise. Capture name, a reliable contact method, location, offering/inquiry type, scope, and timing. Request company, facility, quantities, dates, dimensions, site access, attachments, or other details only where they help qualify that particular enquiry. Budget can be optional. Prefill offering and page context accurately.

Adapt intake to the service. Equipment sales need application and specifications; rentals need dates and fulfillment; high dusting needs height/surfaces/access; moving needs origin/destination and handling; furniture installation needs systems, quantities, plans, and receiving status. Do not use a generic relocation form for every installation enquiry.

Implement accessible labels, autocomplete, clear required/optional fields, client and server validation, useful error messages, submission progress, duplicate-submission handling, success/failure states, and a clear privacy explanation. Preserve entered data on recoverable errors. Do not require marketing opt-in to request a quote. Use separate optional marketing consent where applicable.

Use a configured service or compatible backend for delivery. Keep credentials server-side and out of source control. Validate bot-verification tokens on the server. Check the actual capabilities of any managed form service before relying on it.

Test an authorized clearly labelled submission end to end: the user interface, endpoint response, processing/provider evidence, and receipt in the destination inbox where access allows. Distinguish accepted, queued, saved, notification delivered, and inbox receipt when those states can be observed. An HTTP success response alone does not establish inbox delivery. State exactly what was verified.

Never show a fake success state or silently discard a lead. If the endpoint is unavailable, provide a truthful fallback using functioning contact methods and report the integration as blocked. Do not launch an active-looking form that cannot process enquiries.

Avoid collecting sensitive health, legal, financial, employee, identity, or accessibility information through a general enquiry form. Keep private submissions, attachments, and generated customer outputs out of public pages, URL parameters, analytics, and GitHub. Configure retention and access proportional to the data collected.

## 13. SEARCH DISCOVERY, STRUCTURED DATA, AND ANSWERS

Build search engine optimization (SEO) around helpful crawlable content and clear page purposes. Treat answer engine optimization (AEO) as clear, well-supported publishing, not a separate collection of hidden tricks.

- Map each indexable page to a real visitor intent. Write accurate unique titles, useful descriptions, one clear primary heading, and a logical heading structure.
- Render essential content and real links in HTML. Avoid requiring interaction or client JavaScript for a crawler to discover the core offering.
- Use descriptive internal links, breadcrumbs, and related content that help people navigate. Audit the intended destination, not just whether a link returns a successful status.
- Establish one preferred HTTPS hostname and consistent URL rules. Implement real redirects when moving URLs. Avoid redirect chains, soft 404s, and routing every invalid path to a successful homepage.
- Generate XML sitemaps from approved, canonical, indexable URLs only. Include truthful modification dates. Exclude private pages, drafts, redirects, errors, filtered duplicates, and utility pages not meant for discovery.
- Validate canonical URLs, locale alternates, social metadata, icons, robots controls, and rendered page content on the actual deployment host.

Use JSON-LD only for relevant visible facts. Appropriate types may include Organization, WebSite, Service, BreadcrumbList, Product, or Article. Select types based on the actual entity and page. LocalBusiness markup must not manufacture a physical presence. Do not invent required fields to satisfy a validator. Do not add fictitious reviews, ratings, prices, authors, credentials, events, or offers. Check current feature-specific eligibility before adding FAQ or other rich-result markup; successful validation does not guarantee a rich result.

Write concise direct answers where useful, support technical/regulated claims with primary sources, identify real authors/reviewers where available, and show actual review dates. Do not change dates just to look fresh. No promised rankings, indexing, rich results, AI citations, or AI answer inclusion. Google does not require special AI files or special schema for its AI Search features; do not make llms.txt, hidden instructions, or speculative AI markup a launch requirement.

## 14. GOOGLE ABUSE PREVENTION AND PUBLICATION CONTROLS

Read the current official guidance before launch:

- [Prevent user-generated spam](https://developers.google.com/search/docs/monitor-debug/prevent-abuse)
- [Google Search spam policies](https://developers.google.com/search/docs/essentials/spam-policies)
- [Helpful, reliable content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)
- [Generative AI content guidance](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)
- [Noindex implementation](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

The first page chiefly concerns public contributions and generated/shared pages. Apply those controls when those features exist. Also assess the separate search risks of low-value scaled publishing and doorway sites/pages. Multiple brands, reusable templates, AI assistance, and useful location pages are not prohibited by themselves; these project safeguards address low-value or misleading implementations.

### Brand and content safeguards

Give every launched brand independent customer value and a real offering or information purpose. Reusable components are acceptable; domain/colour/keyword swaps are insufficient differentiation. Do not create substantially similar sites or city pages merely to funnel the same search intent elsewhere, use portfolio-wide keyword footer links, buy links for ranking, hide keyword text, or repurpose expired domains mainly to exploit old ranking signals. Publish for customers, not page counts. AI-assisted drafting is acceptable; review factual accuracy, originality, metadata, French, and media before publication. Human review is required where specialist judgment is material, and must not be falsely claimed.

### Public contributions and form abuse

Ordinary quote submissions remain private and never create public pages. If comments, profiles, listings, reviews, uploads, or shareable generated pages are actually required, implement an abuse policy/report route, moderation, suspicious-activity controls, and appropriate ugc/nofollow link treatment. New unreviewed contributions must not be automatically indexable. Add proportionate rate/volume limits, server validation, and accessible bot controls to public submission flows. Monitor suspicious URL growth, irrelevant search queries, traffic spikes, and Search Console security/manual-action alerts. Do not build a forum or registration system just to implement this section.

### Indexing and privacy are separate controls

Use authentication/authorization for private data. For accessible utility, internal-search, share, or generated-output pages not intended for search discovery, use a proper noindex meta tag or X-Robots-Tag and omit them from sitemaps. A crawler must be able to fetch a page to see noindex; do not rely on a robots.txt block to deliver that instruction. Robots rules and noindex do not secure confidential information. Keep development previews private where supported; otherwise apply deliberate preview indexing controls and verify production is not accidentally excluded.

### Real business representation

Use accurate business identity, contact, and location/service-area information. Do not manufacture storefront, warehouse, or team evidence for Google Business Profile or imply that each domain qualifies for a separate profile. Follow [Google's business representation guidance](https://support.google.com/business/answer/3038177) when a profile is in scope. Website launch alone does not establish profile eligibility.

These safeguards reduce avoidable risk; they are not a guarantee of Google policy approval or search inclusion.

## 15. TECHNICAL ARCHITECTURE, SECURITY, AND PERFORMANCE

Fit the implementation to the actual hosting environment. Preserve a sound existing framework, package manager, and conventions. For a new content/lead site, prefer a maintainable static-first or server-rendered approach with structured content and limited client JavaScript. Choose a stack for the job; do not require Next.js, a single-file generator, Vercel, Supabase, or a database universally.

For WHC hosting, establish the actual plan and runtime support before choosing server dependencies. A static build needs a supported external or compatible server endpoint for forms. Do not assume a cPanel account runs Node services or serverless functions. Document build output, clean URL rules, redirects, asset paths, secrets, HTTPS, and upload/deploy procedures.

For OpenAI Sites, follow the current platform workflow and existing project configuration. Reuse the exact existing project ID; never create a duplicate Site to bypass a source/recovery problem. Track the deployed source revision and project/domain mapping. Do not embed obsolete tool commands in operating instructions; use current supported capabilities.

Keep content structured with explicit draft/published and indexable states. Generate routes, navigation, sitemaps, and locale maps from reliable records rather than scattered duplicated strings. Use a single authoritative contact/configuration record per brand and environment.

Apply proportionate security: server-side validation, output escaping, request/body limits, authorization where needed, restricted administrative access, secret handling, safe dependencies, and supported security headers. For cookie-authenticated state changes, add appropriate cross-site request protections. Frontend validation and honeypots alone are insufficient abuse controls.

For document/photo uploads, allow only needed file types and sizes, validate content appropriately, use safe storage names, keep files private and non-executable, and apply scanning or a supported secure-upload provider where required. If secure uploads cannot be supported, offer a safe alternative rather than publishing an open upload endpoint. Keep sensitive payloads out of logs.

Use HTTPS, optimize principal assets, reserve image space, avoid unnecessary scripts/fonts, and prevent avoidable layout shift. Measure representative production pages on mobile and desktop with available tools. Check current Core Web Vitals guidance; report the test environment and distinguish laboratory results from real-user field data. Do not fabricate scores or claim a passing field assessment for a new site with no field data.

Implement Web Content Accessibility Guidelines (WCAG) 2.2 AA as the target: semantic structure, keyboard operation, visible focus, skip links, contrast, zoom/reflow, meaningful labels, accessible errors, appropriate target sizes, and reduced motion. Use automated checks plus manual interaction checks. Do not label the website certified or fully compliant based on an automated score.

Privacy notices must describe the actual data flow and tools. Load analytics/marketing tools only as appropriate to the approved setup and applicable consent requirements. Track useful events without sending sensitive enquiry content. Never invent analytics IDs, CRM connections, privacy guarantees, or legal compliance claims.
